# EV2-12.1 — Generalized persistent item identity admission

EV2-12.1 generalizes the proven EV2-12 one-off Vampire admission into one
reusable, deterministic, explicitly authorized semantic action for admitting
persistent unique `item:` identities onto the existing RT01 SAVE / publish /
mirror / confirm spine. It creates no new save engine, no parallel
persistence/mirror path, and no automatic identity inference.

> Architecture sentence: **EV2-12.1 does not create a new save system. It
> creates a new authorized semantic admission action on top of the existing RT01
> SAVE / publish / mirror / confirm spine.**

## What this Mission is (and is not)

EV2-12 proved the primitive end to end: `entities/items/vampire.json` declared
the first real Entity V2 item identity and an inert, human-approved one-off SQL
script seeded its first custody. EV2-12.1 replaces the handcrafted per-item SQL
script with one reusable action, so a fresh authorized DM/SAVE workflow can admit
an already-approved unique item without inventing identity, custody, provenance,
or a second persistence engine.

- It **is** one reusable admission action plus a bounded durable admission/
  provenance receipt whose records live on the existing runtime spine.
- It **is not** a generalized identity-intake framework, an automatic
  importance/rarity detector, a bulk import path, an equipment/attunement model,
  a second save engine, or a change to EV2-10/EV2-11 gameplay law.

## Separation of concepts (preserved)

- **definition ≠ instance ≠ custody ≠ provenance.**
- A repository definition (`inventory/...` static mechanics) describes *what an
  item is and how it works*; it does not itself establish a persistent `item:`
  instance, custody, or provenance.
- A reusable definition may correspond to **zero, one, or many** persistent
  instances.
- The authoritative persistent identity key is the stable instance ID
  (`item:<slug>`), **never** a display name, type, rarity, mechanics, narrative
  importance, or inventory presence.
- Multiple identical items are legal: two identical persistent swords are two
  distinct `item:` IDs pointing conceptually to the same/reusable definition
  semantics.
- Ordinary inventory stays quantity-based (EV2-10) and is never auto-promoted.
  Post-admission custody/transfer stays owned by EV2-11.

## Explicit authorization

Admission authority is explicit in the semantic action and its declared request.
Mere ability to call the generic SAVE is **not** mint authority:

- `public.admit_item_identity(<lock_token>, <request>)` is the authorized
  admission action, executable by `service_role` only.
- The generic `stage_campaign_state` / `delete_staged_campaign_state` routes
  cannot write `item_custody` or `item_admissions` at all, so generic SAVE/stage/
  delete can never become an alternate admission path.
- `public.mutate_item_custody(...)` remains non-minting: gameplay updates an
  already-admitted custody record only.

## Request contract

```json
{
  "item_id": "item:<slug>",
  "controller": { "kind": "mainrun" }
              | { "kind": "run", "run_id": "<R##>" },
  "provenance": {
    "source":       <null | non-blank string>,
    "event":        <null | non-blank string>,
    "campaign_day": <null | non-negative integer>
  },
  "owner_entity_id":  <optional, null | character:/party: identity>,
  "holder_entity_id": <optional, null | character:/party: identity>
}
```

- `item_id`, `controller`, and `provenance` are required. Extra fields fail
  closed.
- Initial custody is **optional**: an omitted or explicit-null `owner_entity_id`
  / `holder_entity_id` establishes no custody fact. Unknown owner and Unknown
  holder are valid and are never invented. A known owner/holder is accepted only
  when structurally valid (`character:` / `party:`) and explicitly supplied.
- `provenance` is bounded: `source`/`event` when established, an optional
  campaign day, and nothing else. Unknown stays Unknown. `campaign_day` is a
  declared historical context fact and is never derived from the Clock or
  synthesized.

## Lifecycle

The action runs entirely inside the normal RT01 save lifecycle:

```
begin_campaign_save -> admit_item_identity -> publish_campaign_save
                    -> existing runtime-published mirror / confirmation handshake
```

Within one call it: validates the request and bounded provenance; proves the
asserted controller against authoritative **published** Run truth for every
non-null initial-custody actor (and proves the Run assertion for the empty-actor
case); validates the complete existing candidate `item_custody` and
`item_admissions` collections; enforces the complete **cross-collection**
receipt-to-custody invariant; fails closed on any duplicate/conflicting/replayed
identity; builds and validates the complete resulting collections; then stages
the identity's single custody record **and** its single bounded receipt into the
same candidate generation. A successful runtime admission and its durable receipt
therefore cannot split-brain: they publish together or not at all.

## Bounded admission receipt

`item_admissions` is an engine-owned runtime namespace holding exactly one
bounded receipt per admitted `item:` identity. It is a bounded receipt, not a
history/event subsystem:

```json
{
  "item_id": "item:<slug>",
  "controller": { ...asserted controller... },
  "provenance": { "source": ..., "event": ..., "campaign_day": ... },
  "admitted_generation": <database-owned generation>,
  "admission_version": 1
}
```

The receipt records the explicit declaration plus the successful runtime
admission fact (the database-owned generation). It is written only on success,
so its presence distinguishes a successful admission from a mere request.

### Cross-collection invariant

The two engine-owned namespaces are not validated independently. Before anything
is staged, the action proves the one-directional invariant:

> every `item_admissions` receipt has **exactly one** matching `item_custody`
> record for the same `item_id`.

- **Receipt-without-custody always fails closed**, including a structurally valid
  orphan receipt for an unrelated item: otherwise the action could append a
  different item and republish admission truth that could never have been
  atomically created with its custody.
- **Custody-without-receipt stays allowed.** The asymmetry is forward-only and
  intentional: the pre-EV2-12.1 `item:vampire` admission has custody but no
  receipt because it predates this action. The invariant is not hard-coded to
  `item:vampire`; it is one-directional by construction, so any custody record
  that predates admission receipts is tolerated and is never treated as an
  orphan.

EV2-12.1 receipts are **forward-only**: the EV2-12 `item:vampire` admission
predates this action and has no receipt. That historical asymmetry is legitimate
and is not repaired automatically; a runtime custody record alone never grants
authority to create a missing repository identity record.

## Replay / crash law

- A crash before publication leaves no durable identity or receipt (the candidate
  is discarded); retry admits the same declared instance exactly once.
- A retry after publication fails closed on the already-admitted identity.
- Either way the outcome is deterministic and can never mint a second persistent
  identity or receipt for the same declared instance.

## Same-save authority protection

Admission creates a custody record, so it is a custody-staging operation. It
fails closed when the save has already staged a different `runs` batch, and once
admission is staged every Run-ownership-writing doorway (generic `runs`
stage/delete and RT04 `reconcile_run_resolution`) is refused for the rest of the
save. This reuses the existing EV2-10/EV2-11 operation-fact law; no existing
guard is weakened.

Admission may share one save with an already-authorized inventory mutation when
the gameplay event legitimately requires both: each owning semantic action stays
explicit, and the existing gateway plus a single publication make the result
all-or-nothing.

## What EV2-12.1 deliberately does not build

- **Second real item admission** — later explicit DM/SAVE or Canon Intake
  authorization after this mechanism is merged and proven.
- **Ordinary inventory quantities** — EV2-10.
- **Post-admission ownership/holder transfer** — EV2-11.
- **Equipment/attunement state** — a later dedicated equipment/state gate.
- **Character/NPC real Entity V2 intake** — a later generalized real-entity gate.
- **Homebrew / Official / Adapted provenance taxonomy** — the HB workstream.
- **Bulk campaign history/RAG intake** — later Canon Intake/RAG gates.
- **Generalized entity promotion beyond unique items** and broader
  mount/animal/asset identity semantics — later dedicated gates.

## Proof

`tests/ev2121/` proves the action on real PostgreSQL 15 (and installs cleanly on
PostgreSQL 17) against a freshly rebuilt full migration chain:

- happy path: one authorized already-defined synthetic unique item is admitted
  and publishes identity + first custody + bounded receipt atomically;
- duplicate same-instance admission fails closed (published and same-save);
- conflicting/replayed receipt-without-custody fails closed;
- cross-collection integrity: an orphan receipt (receipt without a matching
  custody record for the same item_id) fails closed even when a different item is
  being admitted, in both published and same-save candidate truth, while the
  forward-only legacy `item:vampire` custody-without-receipt is accepted;
- malformed item ID / request / provenance / controller / custody actor fails
  closed before any staging;
- name collision across distinct item IDs is legal, proving identity is not name/
  type;
- Unknown owner/holder are accepted and never invented; known values are accepted
  only when structurally valid and explicitly supplied;
- established provenance is preserved and unestablished facts stay Unknown;
- malformed/duplicate existing custody or receipt truth fails closed;
- generic gameplay custody mutation remains non-minting;
- generic SAVE/stage/delete cannot bypass the admission action;
- admission does not silently mutate ordinary inventory or unrelated state;
- same-save admission + inventory composition publishes all-or-nothing;
- aborted admission leaves no durable identity/receipt and retry converges on
  exactly one;
- Run/Mainrun controller law and same-save Run-ownership exclusion are enforced.
