# Supabase / PostgreSQL runtime floor

This directory holds the Rolling High Club **published-runtime** PostgreSQL model.
Production target is **Supabase / PostgreSQL**.

## Current foundation

RT01-A establishes the inert published-runtime floor:

- `public.campaign_runtime` — singleton publication locator/head;
- `public.campaign_state_generations` — generation-keyed runtime state;
- `public.campaign_state_runtime` — published-only `security_invoker` projection.

RT01-B adds the guarded SQL Save Gateway:

`BEGIN -> STAGE/DELETE -> ABORT | PUBLISH`

The database owns generation identity and the active save context. Direct runtime-owned DML is blocked for normal tooling; staged state is invisible until publication; stale contexts fail closed; publication advances exactly one generation.

RT01-C adds the external `runtime-published` completion handshake:

`SQL PUBLISH -> mirror pending -> real Git commit -> exact remote SHA read-back -> verifier confirmation -> COMPLETE`

A fresh SQL publication deliberately has `published_git_ref = NULL`. The database mints a `runtime_mirror_token`, and `begin_campaign_save()` refuses generation N+1 until generation N has a confirmed Git mirror. If Git or confirmation fails, retry repairs the same published generation instead of consuming another generation.

The Git worker is `scripts/runtime_published_mirror.py`. It writes the exact published checkpoint to `runtime/published-checkpoint.json` on the separate `runtime-published` branch, verifies the actual remote commit SHA, exact parent continuity, artifact-only commit shape and byte-for-byte checkpoint parity, then confirms that read-back SHA through the narrow `rhc_mirror_verifier` role. Normal `service_role` tooling may read the pending candidate but cannot bind/confirm verifier proof.

For the bootstrap generation, the verifier first durably binds the exact selected `origin/main` base SHA. Confirmation fails closed while that base is still unbound. PostgreSQL JSONB fractional numerics are read through a precision-preserving path before canonical Git serialization. The verifier role itself must be NOLOGIN/non-privileged. On PostgreSQL 16+, RT01-C accepts only the migration/worker login's non-inherited creator ADMIN relationship and its explicit SET path; unrelated or incoming memberships and unsafe attributes fail closed before verifier grants are applied. PostgreSQL 15 retains the original membership-clean installation rule.

RT01-D adds the service-only DM read facade and the guarded engineering-release route while leaving the runtime inert until the separate umbrella activation check.

RT02 adds the **Campaign Clock** as one engine-owned runtime state record keyed `campaign_clock`, without any parallel persistence path:

- `public.stage_campaign_clock(<lock_token>, <clock>)` is the only validated Clock mutation route. It validates the Clock shape and monotonic/coherence invariants against the authoritative published Clock, then stages the absolute target. Replay-safe by construction.
- `stage_campaign_state` / `delete_staged_campaign_state` reject the `campaign_clock` key, closing the generic bypass.
- `publish_campaign_save` derives `campaign_runtime.published_day` from the candidate Clock day, so the locator can never become a second day authority. An Unknown (null) day stays null.

Clock state is `{"schema_version": 1, "day": <null|int>, "phase": <enumerated>, "elapsed_campaign_minutes": <int>, "long_rests_completed": <int>}`. See `docs/CAMPAIGN_TIME.md`.

RT03 adds the **Canonical Run Runtime Read** as the first real domain consumer of that spine, proving the floor can serve one authoritative published Run read without any new persistence path:

- `public.dm_runtime_read_run(<run_id>)` is the supported service-facing Run read. The caller supplies exactly one identity input — a stable `run_id` (`R` + at least two digits) — never Run truth, repository roots, paths, Git refs, generations or schema.
- Run namespace is deterministic and system-owned: the only authoritative Run records are the JSON object entries of the published state key `runs` (a JSON array). Exact identity matching means an entry is a candidate only when its string `run_id` field equals the requested id; arbitrary runtime JSON that merely mentions a run_id-shaped value is discovery noise, never Run authority.
- Success returns the RT01-D runtime metadata envelope for the same published snapshot plus exactly one EV2-08-valid Run record (minimum trusted context — no recursive hydration of Scenarios, Encounters, participants or locations).
- Truthful absence returns `run: null` with the same coherent metadata; nothing is fabricated. Malformed ids, an unreadable `runs` namespace, duplicate claims for one identity, a matching record that violates EV2-08 (including a played Run whose control state is absent or invalid), or a matching Run whose mutable owners are also claimed by another published Run fail closed with no output Run.
- EV2-08 Run semantics are consumed, not redesigned: identity/mode/control-state coherence, identity patterns, unique ID lists and mutable-owner-within-participants are enforced at read time; the requested Run's mutable owners are additionally verified unique against the other published Run entries (the existing EV2-08 Run-vs-Run batch law — one controller token per actor on the Run side only; the broader MAINRUN ownership lifecycle stays outside RT03). Cross-domain resolution (Scenario/Encounter existence, anchor Git reachability) remains owned by the repository EV2-08 validator. Parked control state is preserved truthfully and is never promoted to active authority by a read.
- RT03 is read-only. It stages nothing, seeds nothing, owns no Clock arithmetic (the Run's `campaign_anchor.campaign_time` is returned as the opaque EV2-08 label it is), performs no Git/repository resolution, and adds no mirror code — existing checkpoint mirroring carries published Run state generically.

RT04 adds the **Safe Run Reconciliation** as the first validated domain mutation route that accepts an off-screen Run resolution back into shared authoritative reality, still entirely on the RT01 spine:

- `public.reconcile_run_resolution(<lock_token>, <request>)` runs INSIDE the normal campaign save lifecycle (`begin_campaign_save` → reconcile → `publish_campaign_save`). It resolves the source Run ONLY through the RT03 published read (`public.dm_runtime_read_run`), proves the accepted EV2-09A resolution's lineage and mutable ownership are still legal, and stages only the bounded mutations current repository truth can express.
- The source Run is never caller self-certified; the published `runs` batch decides whether it still exists and what it currently owns. Stale/removed Runs, overlapping or newer mutable owners, malformed or lineage-incoherent proposals, and released owners the Run no longer controls all fail closed before any write. `engineering_release` saves cannot reconcile.
- The bounded translation updates the source Run's own EV2-08 record: the accepted objective result becomes its deterministic `outcome_summary`, and the continuation-vs-collapse law is applied through the request's optional `released_mutable_owners`. A Run that still has owners continues as their current continuation lane; a Run left with zero mutable owners loses its mutable authority (a played Run collapses to `parked`; an off-screen Run keeps `not_applicable`). Historical participation is never erased.
- Accepted consequences that target domains with no legal durable mutation surface yet (entity state, inventory/custody, Hook mutation, location world changes, knowledge) are PRESERVED in the consumption ledger and REPORTED with the exact missing downstream owner; RT04 never invents those subsystems.
- Replay is impossible: an engine-owned `run_reconciliations` consumption ledger keyed by `resolution_id` is staged only by the reconcile route, and the generic `stage_campaign_state` / `delete_staged_campaign_state` routes reject that key (the same closure RT02 applies to `campaign_clock`).
- One reconciliation per source Run per active save: a second distinct resolution for the same `run_id` in the same save is refused even with a fresh `resolution_id`, because it would rebuild the Run from the published record and could resurrect ownership the first reconciliation released. Chaining from a prior save's published result stays legal.
- The complete candidate `runs` batch is validated before anything is staged: no mutable entity may be claimed by more than one Run in the candidate state, and a pre-staged sibling Run claiming an entity the source Run still owns fails closed — `released_mutable_owners` is subtractive-only and is never honored as an ownership transfer. After a reconciliation is staged, the generic routes also refuse further same-save `runs` staging/deletion so the validated candidate cannot be contradicted before publish.
- Preserved unsupported consequences keep their validated human-readable `summary` in the receipt, so consuming a resolution never loses the meaning of what happened.
- RT04 is all-or-nothing through the existing gateway and mirror/confirmation law. It is not a second save engine, has no alternate `reconcile_publish`/generation/mirror path, and is not the future Hard Write Boundary patch.

EV2-10 adds the **owner-local inventory mutation route** as the validated doorway for ordinary possessions + D&D currency, still entirely on the RT01 spine:

- `public.mutate_owner_inventory(<lock_token>, <request>)` runs INSIDE the normal campaign save lifecycle (`begin_campaign_save` → mutate → `publish_campaign_save`). It is the ONLY way to stage the engine-owned `inventory` runtime namespace and is NOT a second save engine.
- Request shape is bounded: `owner_entity_id` (`character:` or `party:`), a `controller` of either `{"kind":"mainrun"}` or `{"kind":"run","run_id":"<R##>"}`, and the absolute target `inventory` record. `controller.kind` must be a JSON string exactly `mainrun` or `run`; a null, missing, number, boolean, array, object, or unknown-string kind fails closed before any authority branch, so a malformed assertion can never fall through to MAINRUN.
- **Controller law consumes authoritative published Run truth** (the RT03 `runs` namespace), never caller prose: if an authoritative published Run currently claims the owner in `mutable_owner_entity_ids`, only that RUN # may author the mutation; if no published Run claims the owner, MAINRUN is the current controller. Historical participation, caller self-assertion, and two Runs claiming one owner all fail closed. A parked played Run that still claims the owner fails closed too (it is not a current controller, and its claim means MAINRUN is not provably the controller), a malformed published `runs` batch (non-object entry, non-string `run_id`, or an EV2-08-invalid record) fails closed rather than skipping the possible claim and falling through to MAINRUN, and a duplicated authoritative Run identity (two valid records sharing one `run_id`) fails closed before any controller is granted.
- **Same-save Run changes and inventory mutations are mutually exclusive**: inventory authority is proven against *published* Run truth, so `mutate_owner_inventory` fails closed when this save has already staged a different `runs` batch, and once this save has staged a successful inventory mutation every Run-ownership-writing doorway is refused — the generic `stage_campaign_state` / `delete_staged_campaign_state` `runs` key and the dedicated RT04 `reconcile_run_resolution` route alike. Closure keys on the explicit inventory-staging **operation fact**, not on final value equality, so a value-equal replay (or a mutate-away-and-back) still closes every doorway; the marker is bound to the save's own database-minted lock token and never leaks into a later save. A former/stale controller can therefore never publish an inventory update through a same-save ownership handoff.
- The record is the EV2-10 evolution of the EV2-03 box: ordinary `entries` are exactly `name` + `description` + `quantity` (both text fields must be non-blank JSON strings; `quantity` is an explicit integer `>= 1` using the owning schema's Draft 2020-12 integer semantics, so `1` and `1.0` agree and non-integral values fail; zero means absence and is never stored; duplicate ordinary entries are rejected like the schema's `uniqueItems` under JSON numeric equality, so `quantity: 1` and `quantity: 1.0` are the same entry), and `currency` is structurally separate with exactly `cp`/`sp`/`ep`/`gp`/`pp`, each a non-negative integral number under the same semantics. An omitted `currency` is coherent, but an explicit `"currency": null` fails closed because a present `currency` must be an object. No category/taxonomy, no owned-asset subsystem, no `item:` identity minting.
- Storage is a single engine-owned runtime key `inventory` holding a JSON array of owner-local records, one record per owner (`entity_id` remains the semantic owner; the collection key is a storage envelope only). Inventory is never duplicated per Run. Character inventory and Party stash share the same shape.
- The generic `stage_campaign_state` / `delete_staged_campaign_state` routes reject the `inventory` key (the same dedicated-key closure pattern as `campaign_clock` and `run_reconciliations`), and the HWB-02 ordinary-save allowlist is preserved unchanged, so a caller/model cannot bypass the validated route with a raw generic runtime write.
- EV2-10 is all-or-nothing through the existing gateway and mirror/confirmation law. It never touches Run design, never creates a second persistence/mirror path, and leaves unique-item identity/custody to EV2-11.

EV2-11 adds the **unique-item custody mutation route** for already-declared persistent `item:` identities, still entirely on the RT01 spine:

- `public.mutate_item_custody(<lock_token>, <request>)` runs INSIDE the normal campaign save lifecycle (`begin_campaign_save` → mutate → `publish_campaign_save`). It is the ONLY way to stage the engine-owned `item_custody` runtime namespace and is NOT a second save engine.
- Request shape is bounded: `item_id` (a valid `item:` identity), a `controller` of either `{"kind":"mainrun"}` or `{"kind":"run","run_id":"<R##>"}`, and required `owner_entity_id` / `holder_entity_id` fields each either JSON `null` or a valid `character:` / `party:` identity. The keys are required so a missing field (SQL NULL) is never confused with an explicit JSON `null`. `controller.kind` must be a JSON string exactly `mainrun` or `run`; a null, missing, number, boolean, array, object, or unknown-string kind fails closed before any authority branch.
- **Owner and holder are independent nullable facts.** `held` (holder non-null), `owned` (owner non-null, holder null) and `treasure` (both null) are derived labels only; there is no stored status field. Gifts/trades may change owner + holder atomically in one mutation, theft/loan changes holder without owner, and a drop clears holder while preserving owner.
- **Non-minting law.** The route updates exactly one already-admitted custody record and fails closed when no admitted record exists for the requested `item_id`. An existing `item_id` counts as admission proof only after the current custody record/collection satisfies the EV2-11 contract, so malformed current truth fails closed and is never canonicalized by overwrite. Gameplay SAVE can never append/mint a new `item:` identity; initial admission/seeding is deferred to EV2-12.
- **Controller law consumes authoritative published Run truth for every involved actor.** The union of every non-null actor across current owner, current holder, new owner and new holder must resolve compatibly under the one asserted controller (MAINRUN or exactly one RUN #), reusing the shared EV2-10 published-Run resolver. This proof runs even when the actor set is empty (the treasure case), so a no-actor mutation cannot bypass controller validation: a malformed or duplicated published `runs` batch fails closed, and a Run assertion must name an existing, non-parked authoritative Run. The full published Run batch must also satisfy the existing EV2-08 cross-Run mutable-owner uniqueness invariant, so two distinct valid Runs claiming the same `mutable_owner_entity_id` fail closed (duplicate `run_id` rejection alone is not sufficient). A malformed published `runs` batch, a parked Run that still claims an actor, two Runs claiming one actor, and a duplicated authoritative Run identity all fail closed. A mutation crossing incompatible MAINRUN/RUN controllers fails closed and must route through the existing reconciliation boundary.
- **Same-save Run changes and custody mutations are mutually exclusive**: the route fails closed when this save has already staged a different `runs` batch, and once this save has staged a custody mutation every Run-ownership-writing doorway is refused — the generic `stage_campaign_state` / `delete_staged_campaign_state` `runs` key and the dedicated RT04 `reconcile_run_resolution` route alike. Closure keys on the explicit custody-staging operation fact, not final value equality, and the marker is bound to the save's own lock token so it never leaks into a later save.
- Storage is a single engine-owned runtime key `item_custody` holding a JSON array of custody records with exactly one record per `item_id`; ordinary `inventory` remains identity-free and is not required to mirror custody.
- The generic `stage_campaign_state` / `delete_staged_campaign_state` routes reject the `item_custody` key (the same dedicated-key closure pattern as `campaign_clock`, `run_reconciliations` and `inventory`), and the HWB-02 ordinary-save allowlist is preserved unchanged.
- EV2-11 is all-or-nothing through the existing gateway and mirror/confirmation law. It never touches Run design, never creates a second persistence/mirror path, and never mints item identity.

It validates the complete existing candidate `item_custody` collection and then the complete resulting collection with the existing EV2-11 validator before staging, and seeds the record with `owner_entity_id` null (ownership remains unknown, not invented) and `holder_entity_id` = `character:gork` (Gork is already established as equipped with and attuned to Vampire, so he is the known current holder). `character:gork` is only a stable reference to the already-established campaign character; no `character:gork` Entity V2 record is created.

EV2-12.1 adds the **generalized persistent item identity admission action**, still entirely on the RT01 spine, and adds no second save engine or mirror path:

- `public.admit_item_identity(<lock_token>, <request>)` is the ONE reusable, explicitly authorized admission action for an already-approved concrete persistent unique item instance. It runs INSIDE the normal campaign save lifecycle (`begin_campaign_save` → admit → `publish_campaign_save` → existing mirror/confirmation handshake) and is executable by `service_role` only. `item_id`, a bounded `controller` (`{"kind":"mainrun"}` or `{"kind":"run","run_id":"<R##>"}`), and a bounded `provenance` object (`source`/`event` when established, optional `campaign_day`; Unknown stays Unknown) are required; initial `owner_entity_id` / `holder_entity_id` are optional and, when absent or JSON null, establish no custody fact and are never invented.
- Identity is declared, never inferred. The stable instance key is the `item:` ID, never a name/type/rarity/presence. Multiple identical items are legal. A reusable definition may correspond to zero, one, or many persistent instances. It never equips/attunes, transfers custody, mutates ordinary inventory quantity, creates relationships, admits characters/NPCs, or redesigns taxonomy.
- The action proves the asserted controller against authoritative PUBLISHED Run truth for every non-null initial-custody actor (and proves the Run assertion for the empty-actor case), validates the complete existing candidate `item_custody` and `item_admissions` collections, enforces the complete existing **and** resulting cross-collection invariant that every `item_admissions` receipt has exactly one matching `item_custody` record for the same `item_id` (receipt-without-custody always fails closed, even for an orphan receipt on an unrelated item), fails closed on any duplicate/conflicting/replayed item identity, validates the complete resulting collections, then stages the identity's single custody record and single bounded receipt into the same candidate generation so a successful admission and its durable receipt cannot split-brain.
- The bounded engine-owned `item_admissions` runtime namespace holds exactly one admission/provenance receipt per admitted `item:` identity (`item_id` + bounded `controller` + bounded `provenance` + database-owned `admitted_generation` + `admission_version`). It is a bounded receipt, not a history/event subsystem. Receipts are forward-only: the EV2-12 `item:vampire` admission predates this action and has no receipt. The cross-collection asymmetry is one-directional by construction: custody-without-receipt (legacy `item:vampire` and any pre-receipt custody) stays allowed and is never an orphan; receipt-without-custody never is.
- Replay/crash law: a crash before publication leaves no durable admission; retry admits the declared instance exactly once. A retry after publication fails closed. Admission creates a custody record, so it is a custody-staging operation: it fails closed when this save has already staged a different `runs` batch, and once staged it closes every Run-ownership-writing doorway for the rest of the save.
- The generic `stage_campaign_state` / `delete_staged_campaign_state` routes reject the `item_admissions` key (the same dedicated-key closure pattern as `campaign_clock`, `run_reconciliations`, `inventory` and `item_custody`), and the HWB-02 ordinary-save allowlist is preserved unchanged. EV2-11's non-minting gameplay law is unchanged: `mutate_item_custody(...)` still cannot mint or append a new `item:` identity.
- No real second item is admitted during BUILD. See `docs/EV2-12.1-GENERALIZED-ITEM-ADMISSION.md`.

EV2-13 adds the **bounded mutable entity-state mutation route**, still entirely on the RT01 spine, and adds no second save engine, controller ledger or mirror path:

- `public.mutate_entity_state(<lock_token>, <request>)` is the ONLY way to stage the engine-owned `entity_state` runtime namespace. It runs INSIDE the normal campaign save lifecycle (`begin_campaign_save` → mutate → `publish_campaign_save` → existing mirror/confirmation handshake) and is executable by `service_role` only.

The box deliberately models no HP, resources, conditions or applied status instances; applied status instances and timing are EV2-13.1.
- **Controller law consumes authoritative published Run truth** (the RT03 `runs` namespace), never caller prose, reusing the shared EV2-10 resolver: under a MAINRUN assertion the entity must be unclaimed by any published Run; under a RUN # assertion it must be controlled by exactly that RUN #. A parked played Run that still claims the entity, two Runs claiming one entity, a malformed published `runs` batch, and a duplicated authoritative Run identity all fail closed. - The generic `stage_campaign_state` / `delete_staged_campaign_state` routes reject the `entity_state` key (the same dedicated-key closure pattern as `campaign_clock`, `run_reconciliations`, `inventory`, `item_custody` and `item_admissions`), and the HWB-02 ordinary-save allowlist is preserved unchanged.
- EV2-13 is all-or-nothing through the existing gateway and mirror/confirmation law. It never changes Run ownership, never creates a second persistence/mirror path or ownership ledger, and never models time-dependent applied status instances.

EV2-13.420 adds the **Temporal Core Foundation** as one small pure mechanical-time contract, and adds no persistence path or mutation authority at all:

- `public.convert_mechanical_duration(<amount>, <from_unit>, <to_unit>)` is the canonical exact duration-conversion primitive. The elapsed-duration vocabulary is bounded to `second`, `round`, `minute`, `hour`, `day` from one seconds table (`round = 6`); `turn` is explicitly rejected as an additive duration unit. `amount` must be a whole non-negative number and the result must be an exact whole number of the target unit, so non-integral/negative/unknown-unit and non-whole results fail closed rather than truncating or rounding. Arithmetic is infinite-precision `numeric`, so only the **final** result is range-checked: a wide seconds intermediate or a wide valid same-unit value (such as bigint-max days → days) is never rejected merely for exceeding bigint, while a genuinely out-of-range final result fails cleanly.
- `public.mechanical_duration_to_campaign_minutes(<amount>, <unit>)` is the narrow RT02 bridge. It returns the exact whole number of campaign minutes or fails closed; a sub-minute duration such as one round (six seconds) never truncates or invents hidden Campaign Clock precision. It is bounded to the actual RT02 `elapsed_campaign_minutes` PostgreSQL integer range (0 through 2147483647): the maximum accepted whole-minute value succeeds and the first value above it fails closed.
- Both functions are pure `IMMUTABLE` and executable by `service_role` only. They stage nothing, publish nothing, and add no table, runtime key, scheduler, status-instance record or sub-minute remainder ledger. RT02's `stage_campaign_clock(...)` absolute-target law remains the only way `elapsed_campaign_minutes` advances. See `docs/EV2-13-420-TEMPORAL-CORE.md`.

EV2-13.1 adds the **timed applied-status continuity** namespace, still on the RT01 spine, and adds no second save engine, controller ledger, world calendar, scheduler or mirror path:

- The engine-owned `applied_statuses` runtime namespace holds exactly one record per stable application identity. A record references an EV2-04.1 `status_effect:<slug>` definition identity (never minting or mutating it), is bound to one `character:` / `creature:` mutable target, carries an optional known source, an engine-derived absolute `applied_at_elapsed_minutes` anchor, a non-empty set of absolute whole-minute threshold due anchors, explicit acknowledgement state and an explicit end anchor. It stores elapsed anchors only — never a world-calendar/date field.
- `public.mutate_applied_status(<lock_token>, <request>)` is the ONLY way to stage `applied_statuses`. It runs inside the normal campaign save lifecycle (`begin_campaign_save` → mutate → `publish_campaign_save` → existing mirror/confirmation handshake) and is `service_role` only. `application_id` and an explicit structurally valid `controller` assertion are required; when creating, an immutable `definition` (definition identity, target, optional source, relative thresholds) is required, and `acknowledge` / `end` are optional additive operations.
- **Timing is elapsed-time only.** The application anchor and every acknowledgement/end anchor are derived from the authoritative published RT02 Clock `elapsed_campaign_minutes`; missing/Unknown Clock truth fails closed rather than defaulting to `0`. Relative human-facing durations are normalized through EV2-13.420's `mechanical_duration_to_campaign_minutes(...)` (a sub-minute duration fails closed; `turn` is never a duration unit), so no duplicate time arithmetic is introduced. The timing definition is immutable after application; reapplication/refresh is deferred.
- **Controller law consumes authoritative published Run truth** for the target mutable actor, reusing the shared EV2-10 resolver. Only the target's current controller (MAINRUN or exactly one RUN #) may mutate/acknowledge/end; a parked claiming Run, two Runs claiming one target, a malformed published `runs` batch and a duplicated authoritative Run identity all fail closed rather than falling through to MAINRUN. One application remains exactly one record across MAINRUN/RUN handoffs — never a per-controller copy.
- **Forward-jump catch-up.** `public.read_timed_applied_status(<application_id>)` is the `service_role`-only pure read; it derives age and due/pending state from the current published elapsed cursor, so an arbitrarily large forward jump exposes every still-unacknowledged crossed threshold with no per-minute ticker. Once acknowledged, a threshold is never re-presented as unprocessed; acknowledgement performs no automatic gameplay consequence.
- **Same-save exclusion.** Applied-status mutation and Run-ownership mutation are refused together in both orderings, and applied-status mutation and Campaign Clock mutation are refused together in both orderings. Closure keys on the applied-status-staging operation fact (bound to the save's own database-minted lock token), so a value-equal replay still closes every Run/Clock doorway and the marker never leaks into a later save.
- The generic `stage_campaign_state` / `delete_staged_campaign_state` routes reject the `applied_statuses` key (the same dedicated-key closure pattern as `campaign_clock`, `run_reconciliations`, `inventory`, `item_custody`, `item_admissions` and `entity_state`), the HWB-02 ordinary-save allowlist is preserved unchanged, and legacy `live_status` is never applied-status authority.
- **World-calendar position is not elapsed time.** A later backwards/forwards world-date placement changes no elapsed anchor and cannot reverse status ageing, produce negative elapsed duration, or infer automatic calendar-based expiry. Harptos/Dalereckoning representation, date jumps, turn-boundary/initiative semantics, stacking/concentration and automatic consequences are deferred. See `docs/EV2-13-1-TIMED-STATUS-CONTINUITY.md`.

### Runtime read priority

1. Call `public.dm_runtime_read()` for bounded current context.
2. Call `public.dm_runtime_read('<query>')` for a targeted published-state lookup.
3. Call `public.dm_runtime_read_run('<run_id>')` for one authoritative published EV2-08 Run by exact identity.
4. Call `public.dm_current_search('<focus>')` for the bounded current records relevant to one exact entity-like focus.
5. Use the `runtime` metadata returned by that same call: generation, current Git ref, day, mirror status and last-confirmed fallback.
6. If SQL is sufficient, stop. If more detail is required, read only the smallest relevant repository source pinned to the returned confirmed ref.

The facade reads only `campaign_runtime.published_generation`; staging/future rows never participate. A zero-hit lookup still returns runtime metadata and `results: []`. While a newer SQL generation is mirror-pending, its current `git_ref` remains `NULL` and the previous confirmed ref is explicitly labelled `stale`, never presented as proof for the current generation. Generation 0 returns Unknown/empty RHC-shaped context without seeding campaign facts. If SQL is unavailable, use only an exact `last_confirmed_git_ref` retained from previously trusted runtime metadata and label it stale. If no previously trusted confirmed ref is available, fail closed: do not discover fallback truth from the mutable `runtime-published` head, bare `main` or any other unconfirmed branch.

`public.dm_quick_context()` projects only compact fields from the RHC owners `daily_recap`, `live_status`, `day_resolution`, `dm_meta` and `narrative_hooks`. Hidden-plan and Hook collections are bounded index entries; full bodies remain in their owning source. `public.dm_runtime_lookup(...)` is the internal bounded deterministic lookup helper beneath `dm_runtime_read(...)`; it is not directly executable by `service_role`, `anon` or `authenticated`, so targeted service reads cannot bypass the runtime metadata envelope.

### Engineering release promotion

`public.begin_engineering_release(<exact-main-sha>)` begins only from a fully confirmed current runtime. PostgreSQL clones the published state into generation N+1, binds that exact engineering target for retry, preserves the current day and rejects stage/delete calls. Publication mechanically compares the candidate with generation N and fails if campaign state or day changed.

The existing mirror worker then proves that the bound target is an exact commit reachable from fetched `origin/main` and that changes since the confirmed runtime stay inside the bounded engineering/runtime-support paths. It creates or reuses one auditable commit with ordered parents:

1. exact previously confirmed `runtime-published` ref;
2. exact bound approved-main target.

The commit tree comes from the engineering target and differs from that second parent only by `runtime/published-checkpoint.json`. Exact remote SHA read-back, canonical checkpoint bytes and verifier confirmation remain mandatory. Failure leaves the same SQL generation and target mirror-pending for retry; it never consumes N+2. Ordinary campaign saves retain RT01-C's one-parent artifact-only behavior.

### Threat model / non-goal

RT01-C proves **durability, continuity and parity** across SQL and Git. It is not a hostile-repository-writer authentication protocol. The designated repository/branch is assumed to remain under normal operator/repository control.

Therefore commit metadata is not an authority surface and RT01-C does **not** require a predetermined unique commit SHA before Git publication. A retry may reuse an already-pushed remote commit when it has the exact expected parent anchor, changes only the checkpoint artifact, and contains the exact canonical bytes for the pending SQL generation. The exact SHA becomes authoritative only after the real remote ref is read back and verifier confirmation binds that SHA to the pending generation/token.

A threat model where another repository writer deliberately races the mirror worker with a same-parent/same-bytes forged commit is outside RT01-C and would require a separate security design mission rather than incremental hardening here.

### Authority model (intended)

- **SQL / Supabase** is intended to become the live operational world surface, but only after RT01-A/B/C/D are all built, proven and the umbrella activation check passes.
- **Pinned Git + `runtime-published`** provide durable checkpoint/provenance proof for the published checkpoint. Consumer-level fallback or recovery semantics belong to RT01-D or a later explicit recovery mission.
- SQL publication and Git recovery proof are separate cross-system stages. A SQL-published generation may exist while Git confirmation is pending; that save is not complete.

These are complementary authority surfaces, not competing copies of the world.

### Inertness

RT01-A/B/C remain foundation only. They do **not** switch RHC live runtime authority to SQL and do not change campaign, canon, or gameplay behavior.
